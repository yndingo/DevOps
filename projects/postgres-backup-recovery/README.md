# PostgreSQL Backup and Recovery in Docker Compose

Учебный DevOps-проект: резервное копирование PostgreSQL,
симуляция потери базы и восстановление из архива с проверкой данных.

## Что реализовано

- PostgreSQL 18 в Docker Compose.
- Тестовые данные: 50 клиентов и 500 заказов.
- Ручные и автоматические бэкапы через pg_dump в формате custom.
- Хранение данных БД и архивов в разных Docker volumes.
- Recovery drill: удаление БД, создание чистой БД и восстановление через pg_restore.
- Проверка количества строк и MD5-подписей содержимого таблиц.
- Замер времени восстановления и возраста точки восстановления.

## Архитектура

```text
Ubuntu Server VM
└── Docker Compose
    ├── db: PostgreSQL 18
    │   ├── pg_data → /var/lib/postgresql
    │   └── backups → /backups
    │
    └── backup-scheduler
        ├── подключение к PostgreSQL по адресу db:5432
        ├── запуск pg_dump с паузой 60 секунд между бэкапами
        └── backups → /backups

Скрипт recovery-drill.sh запускается на VM и управляет
бэкапом, удалением БД, восстановлением и проверкой через docker compose exec.
```

## Запуск

Требования: Linux, Docker Engine и Docker Compose с поддержкой профилей.
Все команды выполняются из корня проекта.

```bash
git clone [https://github.com/yndingo/DevOps.git](https://github.com/yndingo/DevOps.git)
cd DevOps/projects/postgres-backup-recovery
```

Подготовить конфигурацию:

```bash
cp .env.example .env
nano .env
```

В `.env` необходимо заменить `POSTGRES_PASSWORD`.
Для приведённых ниже команд используются
`POSTGRES_USER=devops` и `POSTGRES_DB=devops`.

Выдать скриптам права на выполнение и запустить PostgreSQL:

```bash
chmod +x scripts/*.sh
docker compose up -d --wait db
docker compose ps
```

При первой инициализации PostgreSQL автоматически выполнит
SQL-файлы из `db/init/`.

Проверить количество строк:

```bash
docker compose exec -T db psql -U devops -d devops \
  -c "SELECT count(*) FROM customers;" \
  -c "SELECT count(*) FROM orders;"
```

Ожидаемый результат: 50 клиентов и 500 заказов.

## Ручной бэкап

```bash
docker compose exec -T db /scripts/backup.sh
docker compose exec -T db ls -lh /backups
```

Скрипт создаёт архив во временном файле, проверяет его оглавление
через pg_restore --list и только затем переименовывает в файл .dump.
Проверка оглавления не заменяет тестовое восстановление.

## Проверка восстановления

Внимание: recovery drill удаляет и пересоздаёт учебную БД,
указанную в .env. Не запускать на базе с нужными данными.

Перед запуском остановить планировщик, если он работает:

```bash
docker compose --profile scheduler stop backup-scheduler
./scripts/recovery-drill.sh
```

Сценарий выполняет:

1. Сохранение количества строк и контрольных сумм таблиц.
2. Создание бэкапа.
3. Добавление 25 заказов после бэкапа.
4. Удаление БД и создание пустой БД.
5. Проверку отсутствия таблиц.
6. Восстановление из созданного архива.
7. Сравнение подписей до и после восстановления.
8. Проверку, что 25 заказов, отсутствовавших в бэкапе, потеряны.

Успешный результат: DRILL ПРОЙДЕН УСПЕШНО.
Отчёт и подписи сохраняются в drill/<дата-прогона>/.

## Результаты эксперимента

Два последовательных прогона завершились успешно.
После каждого восстановлены 50 клиентов и 500 заказов;
контрольные суммы до и после восстановления совпали.

| Показатель | Первый прогон | Второй прогон |
|---|---:|---:|
| Измеренное время восстановления с проверкой | 0.7 с | 0.7 с |
| Приблизительный возраст точки восстановления в момент сбоя | 0.6 с | 0.5 с |
| Размер архива по du -h | 12K | 12K |
| Заказы, потерянные после восстановления | 25 | 25 |

[Отчёт второго прогона](docs/drill-report.md).

RTO и RPO являются целевыми требованиями к восстановлению.
В этом проекте целевые значения не задавались:
скрипт измеряет фактическое время восстановления
и приблизительный возраст точки восстановления.

Возраст точки оценивается от момента перед запуском pg_dump.
Значение 0.5 с в эксперименте не означает, что автоматические
бэкапы обеспечивают потерю данных максимум за 0.5 с:
при периодическом запуске окно зависит от интервала,
длительности бэкапов и успешности их выполнения.

## Автоматические бэкапы

Планировщик включается отдельным профилем:

```bash
docker compose --profile scheduler up -d
docker compose logs -f --tail 20 backup-scheduler
```

После каждого успешного бэкапа в логах появляется
[scheduler] backup completed at ...

Ctrl+C завершает просмотр логов, но не останавливает планировщик.

Пауза между завершением одного бэкапа и началом следующего
задаётся BACKUP_INTERVAL_SECONDS в .env.
Для демонстрации используется 60 секунд.

Посмотреть архивы и остановить только планировщик:

```bash
docker compose exec -T db ls -lh /backups
docker compose --profile scheduler stop backup-scheduler
```

После изменения .env нужно повторить
docker compose --profile scheduler up -d,
чтобы Compose применил новую конфигурацию.

## Остановка стенда

Остановить и удалить контейнеры проекта, сохранив данные и архивы:

```bash
docker compose --profile scheduler down
```

Повторно запустить только PostgreSQL:

```bash
docker compose up -d --wait db
```

Не добавляйте флаг -v к команде down, если хотите сохранить данные:
он удаляет именованные volumes проекта, включая pg_data и backups.

## Сброс учебных данных

Внимание: следующая команда удаляет текущую учебную БД
и заново создаёт схему и исходные 50 клиентов и 500 заказов.
Архивы в volume backups не удаляются.

```bash
docker compose --profile scheduler stop backup-scheduler
./scripts/reseed.sh
```

## CI

GitHub Actions при push и pull request выполняет:

- Проверку shell-скриптов через ShellCheck.
- Проверку конфигурации Docker Compose без профиля и с профилем scheduler.

Для подстановки переменных используется .env.example.
Настоящие учётные данные стенда в CI не передаются.

Recovery drill пока запускается вручную и не входит в CI.

## Ограничения

- Это учебный стенд, а не готовая production-система.
- Оба Docker volumes находятся на одной VM:
  потеря VM или её диска может уничтожить и данные, и бэкапы.
- Нет WAL-архивирования и восстановления на произвольный момент времени.
- Нет автоматического удаления старых архивов, шифрования и внешнего хранения.
- Маленький набор данных не позволяет оценивать скорость восстановления больших БД.
